# Распознавание чеков

`ff-ocr` — приватный Python-сервис PaddleOCR. `ff-split` принимает фотографии,
хранит очередь в PostgreSQL и создаёт обычные расходы только после проверки человеком.
Код интерфейса находится в соседнем репозитории FinFlowFront, вкладка события «Чеки».

## Пользовательский сценарий

1. Участник активного события выбирает JPEG, PNG или WebP либо вставляет фото из буфера.
   Локальный предпросмотр требует явного подтверждения отправки; отмена ничего не загружает.
2. API возвращает сохранённую задачу, обработка продолжается независимо от вкладки браузера.
3. Пользователь видит оригинал и распознанные позиции, исправляет названия и суммы,
   выбирает плательщика и участников каждой позиции. Черновик можно сохранить.
4. Подтверждение создаёт выбранные расходы одной транзакцией. При одинаковых участниках
   можно объединить покупки в один расход. Дальнейшие правки выполняются в «Расходах».

OCR ошибается, особенно на смазанных снимках, скидках и мелких цифрах. Совпадение сумм
не доказывает правильность распознавания. Расхождение с напечатанным итогом требует
отдельного подтверждения; если итог не найден, интерфейс показывает предупреждение.
Цена × количество применяется при нечитаемой сумме позиции с понижением уверенности.
Никакие расходы не создаются автоматически.

После неудачного основного прохода (нет позиций или итога) выполняется один дополнительный
проход с официальным классификатором ориентации. Его результат используется только при
наличии позиций, напечатанного итога и их арифметическом совпадении; интерфейс дополнительно
предупреждает об автоматическом повороте. Основной проход с найденным итогом не подменяется.
Повторный проход начинается только если первый занял меньше 30 секунд; это порог начала,
а не жёсткий лимит всей нативной обработки. Ошибка поворота сохраняет исходный черновик.

## Запуск

Официальные источники: [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR),
[документация](https://paddlepaddle.github.io/PaddleOCR/main/en/version3.x/pipeline_usage/OCR.html),
пакеты из PyPI. Веса `PP-OCRv5_mobile_det`, `eslav_PP-OCRv5_mobile_rec` и `PP-LCNet_x1_0_doc_ori`
загружаются PaddleX из официального BOS-хранилища Paddle в `/models`.
Опрос сторонних зеркал отключён. Первое скачивание и загрузка моделей требуют времени;
`/health/ready` становится доступен после загрузки модели.

Из корня репозитория, с настроенными обычными секретами существующего стенда:

```sh
export OCR_TOKEN="$(python3 -c 'import secrets; print(secrets.token_urlsafe(36))')"
export OCR_BASE_URL=http://ocr-gateway:8086
export OCR_WORKERS=1
docker compose --parallel 1 --profile receipts up -d --build
```

Токен должен содержать не меньше 32 символов. Не добавляйте его в Git.
Профиль `receipts` не публикует OCR-порт наружу. Без `OCR_BASE_URL` прежний стек
продолжает работать, маршруты чеков возвращают понятную ошибку 503.

Контейнер использует Python 3.11 и нативную архитектуру хоста. Для Linux/amd64
установлен PaddlePaddle 3.3.0; для Linux/aarch64 — официальный 3.2.2, поскольку у 3.3.0
нет ARM Linux wheel в PyPI. PaddleOCR 3.3.2 и PaddleX 3.3.13 одинаковы. На ARM Mac
для разработки проверен Python 3.13/arm64 с PaddlePaddle 3.3.0.
Запуск OCR вне контейнера:

```sh
python3 -m venv ff-ocr/.venv
ff-ocr/.venv/bin/pip install -r ff-ocr/requirements.txt
export PADDLE_PDX_CACHE_HOME=/absolute/path/to/local/models
cd ff-ocr
.venv/bin/uvicorn app:app --host 127.0.0.1 --port 8086 --limit-concurrency 16
```

`OCR_TOKEN` должен совпадать у ff-split и ff-ocr. `OCR_CPU_THREADS` по умолчанию 2.
Если ff-split работает в контейнере, а OCR на Mac, адрес задаётся через
`http://host.containers.internal:8086`; доступность loopback зависит от runtime.

Настройки ff-split:

| Переменная | Значение / назначение |
| --- | --- |
| `OCR_BASE_URL` | Приватный адрес OCR; пустое значение отключает конвейер |
| `OCR_TOKEN` | Общий приватный Bearer-токен |
| `OCR_WORKERS` | Число фоновых обработчиков на экземпляр ff-split, от 1 до 8 |
| `RECEIPTS_S3_ENDPOINT` | MinIO endpoint без схемы; в compose `minio:9000` |
| `RECEIPTS_S3_ACCESS_KEY`, `RECEIPTS_S3_SECRET_KEY` | Учётная запись приватного хранилища |
| `RECEIPTS_S3_BUCKET` | По умолчанию `finflow-receipts` |
| `RECEIPTS_S3_TLS` | TLS для S3, по умолчанию false в локальном compose |

В compose существующие MinIO credentials передаются только через окружение.
Проверка существующего бакета запрещает любую установленную политику: не допускается
ни публичный бакет, ни запуск без возможности проверить политику. Внешних URL от
пользователя сервис не загружает. Фотографии доступны через авторизованный API события.

## Очередь, ограничения и восстановление

- Миграция `000007_receipts` добавляет задачи и outbox; `000008_receipt_actions` —
  мягкое удаление, повтор OCR, признак доступности фото и отдельный журнал допуска.
- Допуск выполняется **до записи в S3**: не более 3 активных задач пользователя,
  50 загрузок и ручных повторов на пользователя за скользящие сутки, 500 таких операций
  на весь сервис за сутки и 1000 активных задач во всём стенде.
  Архивные события не занимают активную квоту, но учитываются в суточной. Удаление
  чека или события не обнуляет её: журнал допуска хранится 7 дней, очистка пакетная.
- Миграция `000009_receipt_read_budget` добавляет долговечный бюджет чтений фото:
  200/пользователь и 1000/сервис за скользящие сутки. Учитываются GET изображения,
  preflight ручного повтора и каждое чтение OCR-воркера (за счёт пользователя, поставившего задачу).
  Проверка проходит до S3; автоматические повторы останавливаются при исчерпании бюджета.
  Очистка журнала старше двух суток пакетная, рестарт и удаление чеков лимит не сбрасывают.
- Квоты сериализуются короткой advisory-блокировкой; запросы счётчиков ограничены
  порогами и используют отдельные индексы. Во время OCR SQL-транзакция не удерживается.
- SHA-256 изображения уникален среди неудалённых чеков события. Повторная загрузка возвращает
  существующий чек без новой записи фото. Это не поиск визуально похожих снимков:
  другая компрессия или кадрирование создадут другой хеш.
- Если запись фото завершилась ошибкой, API возвращает безопасный 503 с просьбой повторить
  отправку. Тот же файл восстанавливает прежний черновик с новым ключом объекта и повторным
  допуском по квотам; сохранённые правки остаются. Старые PUT и очистка прежнего ключа
  не затрагивают новое фото. Обычная повторная загрузка готового чека сохраняет открытые
  несохранённые правки интерфейса.
- Размер файла до 10 МиБ, до 16 млн пикселей и до 12000 пикселей по каждой стороне.
  На экземпляре API общий бюджет 4 одновременных загрузок/выдач фотографий; сверх него 429.
  Чтение HTTP/S3 ограничено 30 секундами, запись HTTP — 60 секундами.
- `FOR UPDATE SKIP LOCKED` выдаёт задачу одному обработчику; lease 120 секунд,
  OCR HTTP timeout 90 секунд, весь этап обработки 95 секунд. Устаревшие результаты
  не перезаписывают новое состояние благодаря lease token.
- Завершённый черновик можно распознать повторно: исходная ревизия идемпотентна,
  попытки и 15-минутный период восстановления начинаются заново. Суточный и активный
  лимиты учитывают пользователя, запросившего повтор. Сохранённые правки не заменяются.
  Фото с начатым/завершённым удалением повторно в очередь не попадает.
- Обычно не больше 3 автоматических попыток. 429/503 и сетевые сбои откладываются без расхода попыток
  в первые 15 минут жизни задачи; после этого действует обычный конечный бюджет.
- Один Python-процесс обрабатывает одно изображение. Отмена HTTP не освобождает
  слот до завершения нативного расчёта. Перегрузка получает быстрый 429 с Retry-After.
- Пакет до 100 позиций, деньги в целых копейках. Ревизия защищает от потери правок;
  повтор того же подтверждения возвращает созданные ID. При ошибке одной позиции
  откатываются все расходы, история и состояние чека.
- Архив запрещает загрузку и подтверждение. Очередь архивного события приостанавливается;
  уже запущенный OCR может сохранить технический результат без создания расходов.
- «Удалить черновик» скрывает неподтверждённый чек и отменяет его аренду; поздний
  результат OCR или PUT не воскрешает запись. Чеки с уже созданными расходами
  сохраняются для просмотра и повторного подтверждения без дублей.
- Неподтверждённые чеки без активности 30 дней очищаются пакетами по 100. Повтор OCR
  или сохранение правок продлевает этот срок, но не меняет дату первоначальной загрузки. Подтверждённые
  сохраняются вместе с событием. Окончательное удаление архивного события через 6 месяцев
  каскадно удаляет чеки; триггер сохраняет ключи фотографий в outbox.
- Объекты удаляются спустя час после попадания в outbox. Неудачные удаления повторяются.
  Очистка пропускает строки, одновременно подтверждаемые или арендуемые обработчиком.

## Наблюдение и масштабирование

`GET /health/live` и `/health/ready` не требуют токена. `GET /metrics` и
`POST /recognize` требуют `Authorization: Bearer ...`; документация FastAPI отключена.
Метрики содержат completed, failed, busy и суммарное время. Исходные чеки и токены
не пишутся в прикладные логи.

Высокая скорость API не означает такую же скорость распознавания. В профиле `receipts`
есть приватный `ocr-gateway` на официальном HAProxy 3.2. Он использует DNS контейнерной
сети, проверяет readiness и направляет не более одного запроса в каждый OCR-процесс.
Индивидуальная очередь каждого сервера ограничена одной задачей; дополнительно HAProxy
имеет общую очередь backend. Общий предел gateway — 16 соединений, ожидание очереди —
не более двух секунд. Перегрузка возвращается в PostgreSQL-очередь через ограниченный retry.
Токен проверяет OCR; gateway и OCR не публикуют порты на хост.
[Правила DNS HAProxy](https://docs.haproxy.org/3.2/configuration.html#5.3).

Для двух реплик сначала запустите одну и дождитесь healthy, чтобы полностью подготовить
общий том официальных моделей. Затем, до подачи пользовательской нагрузки:

```sh
export OCR_WORKERS=2
docker compose --profile receipts up -d --no-build --scale ff-ocr=2
```

Одновременно холодные реплики в один пустой кэш не запускайте. Gateway поддерживает
до восьми адресов; ресурсы CPU/RAM и число обработчиков ff-split согласуются с репликами.
На небольших машинах собирайте сервисы отдельными командами. BuildKit/Bake может
обрабатывать несколько targets даже при `--parallel 1`; этот флаг сам по себе
не гарантирует общий лимит памяти сборки.
Память VM должна вмещать OCR-процессы, остальные сервисы и сборку: лимит одного OCR
в compose — 2 ГиБ, а не бюджет всего стенда. В локальной VM с 2 ГиБ полноценная
нагрузка двух Linux-реплик не поместилась; функциональная и нагрузочная проверки
такой конфигурации — разные вещи.
Штатная полная сборка всех образов с нуля проверена в отдельной Linux/arm64 VM с 8 ГиБ.
Локальные замеры и ограничения качества записаны в [evaluation.md](evaluation.md).

## Тесты

```sh
ff-ocr/.venv/bin/pip install -r ff-ocr/requirements-test.txt
ff-ocr/.venv/bin/pytest ff-ocr/tests -q
cd ff-split
go test ./...
go test -race ./tests ./internal/adapters/receiptimages -run 'Receipt|ExistingBucketPrivacy'
```

Go integration tests требуют Docker-совместимый runtime и создают изолированные PostgreSQL-контейнеры.
Python-тесты подменяют тяжёлую модель и проверяют парсер, авторизацию, лимиты,
перегрузку и отмену. Оценка настоящей модели запускается отдельно по локальному корпусу.

Повторный прогон настоящей модели по уже скачанным локальным изображениям:

```sh
ff-ocr/.venv/bin/python ff-ocr/evaluate.py /absolute/path/to/corpus/manifest.json --output /tmp/finflow-evaluation.json
```

Манифест — JSON-массив объектов с `file`, `source`, `license`, `sha256`. Фотографии
должны лежать внутри каталога манифеста. Скрипт проверяет хеши, но не скачивает фото
и не считает разметку корпуса достоверной оценкой точности.

## Повторение нагрузки

`benchmark.py` работает только с loopback HTTP-адресами. Режим `admission` создаёт
собственные синтетические аккаунты и события, загружает уникальные проверенные SHA-256,
ждёт конечных статусов и проверяет отсутствие расходов. После прогона отзывает свои
сессии; токены и пароли в отчёт не входят. Запускайте на одноразовом стенде.
Отчёт отдельно считает принятые задания, HTTP-отказы и транспортные ошибки.

```sh
.venv/bin/python benchmark.py admission /absolute/path/manifest.json --concurrency 4 --output /tmp/admission.json
# Отдельный перегрузочный запуск с новыми событиями:
.venv/bin/python benchmark.py admission /absolute/path/manifest.json --concurrency 8 --output /tmp/overload.json
```

Для сравнения OCR используйте одинаковый набор фото, предварительно прогрейте каждую
реплику и запускайте `ocr` с concurrency 1/2 при одной/двух репликах. Сравнивайте только
полные прогоны `all_completed=true`; батч с 429/503 характеризует отказы, а не throughput.
Приватный OCR Bearer-токен передаётся через `OCR_TOKEN`, адрес — через `--ocr-url`.
По умолчанию примеры ожидают временные локальные порты 65170/65171/65172; в обычном
compose OCR остаётся приватным, для замера используйте отдельный локальный override.


## Проверка зависимостей в CI

`.github/workflows/security.yml` запускает тесты и `govulncheck` приложений,
тестовых пакетов и Go-инструментов всех шести модулей. Python проверяется
`pip-audit --strict` вместе с `requirements-test.txt` на Linux x86_64 и aarch64;
это разные ветки Paddle в requirements. После установки выполняются тесты и
собирается граф фактически разрешённых Python-зависимостей.

`scripts/security/dependency_snapshot.py` формирует данные GitHub Dependency Graph:
для Go — реальные импорты приложений, тестов и инструментов с учётом `replace`;
для Python — транзитивные зависимости от production/test requirements с учётом
platform markers и extras. Посторонние пакеты runner и неиспользуемые опциональные
ветки полных Go module graphs не выдаются за зависимости собранных приложений.
Локальные Go-модули учитываются как исходники текущего checkout, а не старые remote pseudo-versions.

JSON-файлы передаются через artifacts. Только после успешных проверок **всех**
модулей и обеих Python-платформ отдельный job с `contents: write` отправляет
снимки точного commit в GitHub. PR jobs имеют только чтение; токен публикации
не передаётся коду PR. Публикации сериализованы, каждый POST проверяет актуальный
remote main, поэтому медленный старый workflow не возвращает старый граф.
Корреляторы стабильны по модулю/платформе: следующие запуски заменяют данные,
а не добавляют бесконечные устаревшие снимки. При пропущенной платформе,
неразрешённом пакете или неполном наборе artifacts публикация завершается ошибкой.

Сбор данных сам по себе не требует GitHub-токена; для локальной диагностики:

```sh
python3 scripts/security/dependency_snapshot.py go --module ff-files --output /tmp/files-dependencies.json
# В окружении с установленными production и test requirements:
python scripts/security/dependency_snapshot.py pip --output /tmp/ocr-dependencies.json
python -m unittest discover -s scripts/security -p 'test_*.py'
```

Неподтверждённые/грязные локальные графы публиковать нельзя. Предупреждения
Dependabot вручную не скрываются: GitHub получает текущие версии и пересчитывает
alerts по ним. Документация API и правила приоритета: [GitHub Dependency Graph](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-graph-data).
